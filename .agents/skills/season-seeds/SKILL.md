# Season seeds (weekly plants)

Mirror of `weekly-visitor` for plants. Paths relative to `models/`; shipped models (specs, roster, assets) are in the board dir `models/board/`. Run after weekly-visitor step 0c (hydrate), or do it yourself when run alone (`pnpm board seed`, then weekly-visitor 0c's hydrate). Rules: SPEC.md Garden ("When a plant finishes", "3D plants, one per plant"). Each plot (habit) grows one plant at a time; when it blooms or dies it shows that for a week, then the next plant goes in. Every plant gets its own species, made here, just in time. No stock is made ahead.

When: every week, after the visitor (`weekly-visitor` step 1c), or by hand.

No spoilers (weekly-visitor "No spoilers"): messages call each plant by its plot and gen, never its species, name or look.

0. Preflight `./setup.sh --check`.
1. Inputs: `checks/game_status` `value.garden` (`season` = calendar season name, `biome`, `needs`; else ask). `needs` = `[{plot, habit, gen, rarity, mutated, biome, sown}]`: one entry per plant with no model yet. Skip an entry whose roster plant (`plot` + `gen`) already exists. Empty → report "no plants needed" and stop. Also read that biome's `biomes.json` entry and the roster's plants.
2. **One subagent per entry, in parallel** (Agent tool, `model: "sonnet"`, all spawned in one message, in the background; AGENTS.md "Subagent models"). Each subagent owns one plant's making; you (the orchestrator) own its **judging**, because subagents have no Agent tool and cannot spawn judges (dry run 2026-11-24). Give each only ids and paths: the entry (`plot`, `habit`, `gen`, `rarity`, `mutated`, `biome`, `sown`), the season, and this skill's path. Subagents never touch shared files (`roster.json`, git, the artifact): those are step 3b. The machine caps concurrent Blender jobs itself (`shared/tools/slots.py`, held by every `build.py` and `verify.sh`; `LB_BUILD_SLOTS`, default half the cores) and credits queued time back to each ledger (`minutes_queued`), so spawn every entry at once.
   **Per-plant chain (the subagent).** Start the ledger when it starts: `python3 models/shared/tools/ledger.py start plant-<plot>-g<gen> --rounds 4 --minutes 30`. The model id is the species id from `plant-brief` (snake_case, 3-32 chars), never the plot (plots may hold hyphens). `plant-brief` → `model-build` (`blender -b --factory-startup --python shared/blender/build.py -- models/board/plant/specs/<id>.json --run <run_id>`) → `plant-grow` → `VERIFY_RUN=<run_id> models/shared/tools/verify.sh <id>` (about 10 minutes on software GL: run it with a Bash timeout of 600000 ms or in the background with Monitor, never with the default 2-minute timeout). When the code gates pass and the renders exist, look at `qa/contact.png` yourself (the Read tool shows images; plant-grow's stage check) and fix anything plainly broken before spending a judge round, then **stop and return** `{status: "ready_for_judges", plot, gen, id, run_id, spec, qa: "models/out/<id>/qa"}`. A build that fails the code gates is fixed and rebuilt by the subagent itself (retries per weekly-visitor) before it returns.
   **Judging (you, per plant, as each `ready_for_judges` arrives; other plants keep building).** Run model-verify's judge-panel for that `id` under its `run_id` (fresh judges, each recorded with `ledger.py judge <run_id> <id> <agent> --reply -`), then `judge_verdict.py plant <run_id> <id>` and `ledger.py notes <run_id> <id>`. Send the verdict JSON and the notes back to **the same subagent** (SendMessage to it; it keeps its context). It then continues: PASS → model-verify "Polish rounds" (each counted rebuild comes back as `ready_for_judges`) or finish; FAIL with budget left → `ledger.py plan`, fix the cause, rebuild, return `ready_for_judges` again; budget spent → `ledger.py best <run> <id> [--below-bar]`. To finish, it runs `model-ship` steps 1–2 (optimize, re-check the shipped copy, wrap `models/board/assets/<id>-glb.js`) and returns `{status: "done", plot, gen, id, outcome: "pass"|"below_bar"|"quarantined", roster_entry, ledger: <ledger.py status>, retro: [..]}`, with no species, name or look in any text it returns.
3. Fallbacks (the subagent, steered by your verdicts): route fix notes to the step that owns them. Simplify the plant's own generator first (drop the accessory and the newest parts, keep what makes it read as the species); only if that still fails the code gates, fall back to the closest growth form as is (spec names it, with `notes.why_library_form` saying it is a fallback), never straight to `stem_bloom` by habit. Budget spent without a PASS → ship the best attempt below the bar (weekly-visitor fallback 2; automated gates must pass). Only when no build passed the automated gates → quarantine `out/quarantine/<id>/`, move the spec to `plant/specs/quarantined/<id>.json`, return `quarantined`. The plot keeps its SVG species (it has no model yet); next week's run tries again.
3b. **Orchestrator, once every subagent returned `done`**: append each `roster_entry` to `models/board/roster.json` `models[]`, then model-ship steps 4–5 once for all of them (one commit, one PR, one model-only publish with every id; the visitor rides along). A subagent that dies or never returns `done` counts as quarantined for the report; its ledger says how far it got.
4. Report (orchestrator, from the subagents' returns): plants shipped (plot, habit, gen, rarity, passed or below bar), gates, ledger status, anything quarantined. No species, name, look or accessory. model-ship publishes the live board (pre-approved; AGENTS.md Publish).
5. Retro (AGENTS.md "Improve as you go"): merge the subagents' `retro` lists; one line per problem this run hit, and the fix to this skill, plant-brief, a gate or a tool, made in the same commit.

page-test runtime for plants: `test.html#eco` (lifeboard-setup), a plot of the new species renders all five stages in the Garden card (garden package `plotSVG`), no console errors.
